# 31: Связь нескольких процессов через Unix domain socket (Мультиплексирование)

## 1. Подготовка рабочего места
Переходим в директорию задания и создаем новую папку:

cd ~/MyOSTest
mkdir task_31
cd task_31

## 2. Ключевые концепции для понимания задачи

• Мультиплексирование (I/O Multiplexing): Механизм, позволяющий одному процессу (серверу) отслеживать множество файловых дескрипторов одновременно, не создавая отдельный поток или процесс для каждого клиента.
• Параллельность без задержек: Сервер не блокируется в ожидании данных от одного клиента. Он обрабатывает данные по мере их поступления от любого из подключенных клиентов. Вывод преобразованного текста разных клиентов может смешиваться.
• Обработка отключений: Критически важный момент. Когда `read` возвращает 0 (EOF), это означает, что клиент закрыл соединение. Дескриптор нужно немедленно закрыть и удалить из массива отслеживания, иначе `poll` будет постоянно сигнализировать о готовности (busy loop).

## 3. Шпаргалка: Мультиплексирование ввода-вывода (poll)

СТРУКТУРЫ И ФУНКЦИИ (poll.h)
• struct pollfd: Структура для отслеживания состояния файлового дескриптора.
  - fd: Файловый дескриптор (или -1, если слот не используется).
  - events: Битовая маска событий, которые нас интересуют (например, POLLIN).
  - revents: Битовая маска событий, которые фактически произошли (заполняется функцией poll).

• int poll(struct pollfd *fds, nfds_t nfds, int timeout): 
  Ожидает события на массиве дескрипторов.
  - fds: Массив структур pollfd.
  - nfds: Количество элементов в массиве (не размер в байтах!).
  - timeout: Время ожидания в миллисекундах (-1 = бесконечно, 0 = немедленный возврат).
  - Возвращает: количество дескрипторов, готовых к операции, 0 (таймаут) или -1 (ошибка).

КОНСТАНТЫ СОБЫТИЙ
• POLLIN: Есть данные для чтения (или сокет закрыт клиентом).
• POLLOUT: Можно писать без блокировки.
• POLLERR: Произошла ошибка на дескрипторе.
• POLLHUP: Соединение разорвано (Hang Up).

ВАЖНЫЕ НЮАНСЫ
• При разрыве соединения клиентом `poll` вернет флаг `POLLIN`, но последующий вызов `read()` вернет 0.
• `poll()` не имеет жесткого ограничения на количество дескрипторов (в отличие от `select` и его макроса `FD_SETSIZE`, который обычно равен 1024).
• Unix domain сокеты при закрытии клиентом не генерируют `SIGPIPE` на сервере автоматически при чтении; мы просто получаем 0 байт от `read()`.

## 4. Основные библиотеки

#include <stdio.h>        // printf, perror

## 5. Алгоритм решения

**Сервер (server.c):**
1. Подготовка: Вызовите `unlink()` для удаления старого файла сокета. Создайте сокет через `socket(AF_UNIX, SOCK_STREAM, 0)`.
2. Привязка и прослушивание: Настройте `sockaddr_un`, вызовите `bind()` и `listen()`.
3. Инициализация массива poll: 
   - Объявите массив `struct pollfd fds[MAX_CLIENTS + 1]`.
   - Установите `fds[0].fd = server_fd` и `fds[0].events = POLLIN`.
   - Заполните остальные элементы массива значением `fd = -1` (маркер свободного слота).
   - Установите переменную `nfds = 1` (количество активных дескрипторов для проверки).
4. Главный цикл мультиплексирования (`while`):
   - Вызовите `poll(fds, nfds, timeout)`. Таймаут (например, 1000 мс) нужен для периодической проверки флага завершения программы (например, по Ctrl+C).
   - Если `poll` вернул > 0, пройдитесь циклом по всем элементам массива до `nfds`.
   - Если `fds[i].fd == -1`, пропустите итерацию.
   - Если `fds[i].revents & POLLIN`:
     - **Если это слушающий сокет (`server_fd`)**: вызовите `accept()`. Найдите первый свободный слот (`fd == -1`) в массиве, запишите туда новый `client_fd`, установите `events = POLLIN`. Если новый индекс >= `nfds`, увеличьте `nfds`.
     - **Если это клиентский сокет**: вызовите `read()`. 
       - Если `bytes_read > 0`: преобразуйте буфер в верхний регистр (`toupper`) и выведите на экран.
       - Если `bytes_read == 0` (или ошибка, кроме `EINTR`): клиент отключился. Закройте сокет (`close`), установите `fds[i].fd = -1`. Оптимизируйте `nfds`, сдвинув границу влево, если последние слоты пусты.
5. Завершение: По сигналу завершения закройте все активные сокеты и вызовите `unlink()` для файла сокета.

**Клиент (client.c):**
1. Создание и подключение: Создайте сокет, настройте `sockaddr_un` и вызовите `connect()`.
2. Отправка данных: В цикле отправляйте сообщения через `write()`. Можно добавить небольшую задержку (`usleep`) между отправками, чтобы наглядно продемонстрировать параллельную обработку на сервере при запуске нескольких клиентов.
3. Завершение: Закройте сокет через `close()`, что отправит серверу сигнал EOF.

## 6. Сборка и тестирование

Создайте Makefile для сборки server.c и client.c:

CC = gcc
# Макрос POSIX и библиотеки сокетов, специфичные для Solaris/Illumos
CFLAGS = -O2 -D_POSIX_C_SOURCE=200112L
LDFLAGS = -lsocket -lnsl
TARGETS = server client

all: $(TARGETS)

server: server.c
	$(CC) $(CFLAGS) -o server server.c $(LDFLAGS)

client: client.c
	$(CC) $(CFLAGS) -o client client.c $(LDFLAGS)

clean:
	rm -f $(TARGETS) *.o socket

.PHONY: all clean

Команды для запуска:
make clean
make

## 7. Пример проверки

**Важно:** Для полноценной проверки мультиплексирования откройте три окна терминала.

**Терминал 1 (Сервер):**
./server
Ожидаемый вывод:
[СЕРВЕР] Запущен. Ожидание подключений на ./socket...
[СЕРВЕР] Нажмите Ctrl+C для остановки.

**Терминал 2 (Клиент А):**
./client Client_A

**Терминал 3 (Клиент Б):**
./client Client_B

**Наблюдайте за Терминалом 1 (Сервер):**
Вы должны увидеть, что сообщения от `Client_A` и `Client_B` приходят и обрабатываются параллельно, без ожидания, пока один клиент закончит передачу. Вывод будет перемешан, что соответствует требованию задачи:

[СЕРВЕР] Новый клиент подключен (fd=4). Всего: 1
[СЕРВЕР] Новый клиент подключен (fd=5). Всего: 2
[Клиент 4]: [CLIENT_A] HELLO FROM CLIENT!
[Клиент 5]: [CLIENT_B] HELLO FROM CLIENT!
[Клиент 4]: [CLIENT_A] THIS IS A TEST MESSAGE.
[Клиент 5]: [CLIENT_B] THIS IS A TEST MESSAGE.
[СЕРВЕР] Клиент 4 отключился.
[СЕРВЕР] Осталось клиентов: 1
[СЕРВЕР] Клиент 5 отключился.
[СЕРВЕР] Осталось клиентов: 0

**Проверка файла сокета:**
Во время работы сервера в директории можно увидеть файл сокета:
ls -l socket
Ожидаемый вывод:
srwxr-xr-x 1 user user 0 ... socket
(Обратите внимание на символ 's' в начале строки прав доступа — он указывает на тип файла "сокет").
