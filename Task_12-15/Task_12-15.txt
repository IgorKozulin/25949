12. Командный интерпретатор shell (задание №1 по shell)
В этом упражнении вы должны разработать упрощенную версию командного интерпретатора системы UNIX - shell. В дальнейшем этот shell будет улучшен добавлением программных каналов и обработки сигналов. Для вас заранее написаны некоторые функции этой программы. В файле shell.c содержится скелет функции main() с комментариями, говорящими, где следует вставить ваш код. Функция main() вызывает функцию promptline() из файла promptline.c, которая читает строку из стандартного ввода. Затем main() вызывает parseline() из файла parseline.c, которая проверяет ввод на отсутствие синтаксических ошибок. Для каждой команды в строке, parseline() формирует дескриптор команды типа struct command, определенного в shell.h. Существует глобальный массив таких структур, называемый cmds[] и объявленный в shell.c. Дескриптор команды состоит из двух полей. Первое поле - массив указателей, называемый cmdargs[]. Функция parseline() инициализирует этот массив указателями на строки - аргументы. Каждый аргумент завершается нулевым байтом. Во входной строке аргументы разделяются пробелами. Кроме того, parseline() помещает после последнего аргумента в списке cmdargs[] нулевой указатель. Команды могут разделяться переводом строки, точкой с запятой, амперсендом (&) или символами <, >, >> или |. Другие глобальные переменные, объявленные в shell.c, определяют, должна ли команда быть запущена в основном (foreground) или фоновом (background) режиме, а также для перенаправления ввода/вывода из/в файл. Эти переменные (bkgrnd, infile, outfile и appfile) устанавливаются в функции parseline(). Если bkgrnd ненулевой, команда должна быть запущена в фоновом режиме, то есть ваш shell не должен ожидать завершения соответствующего процесса. Если infile ненулевой, он указывает на имя файла, из которого должен быть получен стандартный ввод первой команды в строке, т.е. символ <. Аналогично, если outfile ненулевой, он указывает на имя файла, куда следует перенаправить вывод последней команды в строке, т.е. символ >. Наконец, если appfile ненулевой, это имя файла, к содержимому которого следует добавить вывод последней команды в строке, т.е. символ >>. В следующих упражнениях вы будете модифицировать shell.c. Каждое последующее упражнение является улучшением предыдущего. Вы должны использовать следующую версию вызова exec(2):
execvp(cmds[i].cmdargs[0], cmds[i].cmdargs);

## 2. Ключевые концепции для понимания задачи
• Архитектура shell (REPL): цикл «вывести приглашение → прочитать строку → разобрать строку → выполнить команды → повторить». В этой задаче реализуется всё, кроме выполнения.

• Дескриптор команды: cmds[i].cmdargs — массив аргументов в стиле argv, завершённый NULL; cmds[i].cmdflag — битовые признаки места команды в конвейере (OUTPIP, INPIP).
• Аргументы и команды: пробелы и табуляция разделяют аргументы ОДНОЙ команды; символ ';' разделяет независимые команды в строке. Возврат parseline() — количество команд.
• Метасимволы '<', '>', '>>', '&' не попадают в cmdargs: парсер изымает их и сохраняет в отдельных переменных.
• Цель задачи 12: собрать каркас и увидеть результат разбора строки в отладочном выводе. Запуск процессов — задача 13, фоновый режим — задача 14, перенаправления — задача 15.

## 3. Шпаргалка: выданные функции и структуры
• int promptline(char *prompt, char *line, int sizline): выводит приглашение через write(1, ...) и читает строку через read(0, ...). Возвращает число прочитанных байтов, 0 при EOF (Ctrl+D). Приглашение выводится самой функцией, fflush(stdout) не требуется.
• int parseline(char *line): разбирает строку, изменяя сам буфер (разделители заменяются на '\0'). Возвращает число команд (> 0), 0 для пустой строки, -1 при синтаксической ошибке (при этом печатает "syntax error").
• struct command { char *cmdargs[MAXARGS]; char cmdflag; }: MAXARGS = 256, MAXCMDS = 50; cmdargs всегда завершается NULL.
• Биты cmdflag: OUTPIP = 01 (у команды есть выход в канал), INPIP = 02 (у команды есть вход из канала). Печатать удобно в восьмеричном виде (%o).
• Глобальные переменные, которые ОБЯЗАНЫ быть определены в shell.c: struct command cmds[MAXCMDS]; char *infile, *outfile, *appfile; char bkgrnd; (в shell.h они объявлены как extern).
• Условная компиляция: блок #ifdef DEBUG ... #endif собирается только при флаге -DDEBUG.
• Вспомогательные функции внутри parseline.c: strpbrk (поиск ближайшего разделителя), isspace (пробельный символ), blankskip (пропуск пробелов).

## 2. Ключевые концепции для понимания задачи
• fork(): создаёт дочерний процесс — копию родителя, включая массив cmds[] и открытые файловые дескрипторы. Возвращает 0 в потомке, PID потомка в родителе, -1 при ошибке.
• execvp(): заменяет образ дочернего процесса новой программой, ищет её в PATH. При успехе не возвращается, поэтому код после него выполняется только при ошибке.
• waitpid(): родитель (shell) приостанавливается до завершения конкретного потомка. Без ожидания приглашение перемешается с выводом команды, а завершившиеся дети станут «зомби».
• Код завершения: статус, полученный waitpid, «сырой»; его разбирают макросы WIFEXITED / WEXITSTATUS / WIFSIGNALED.
• Последовательное выполнение: команды, разделённые ';', запускаются одна за другой, каждая со своим ожиданием.
• Упрощение этой задачи: infile, outfile, appfile, bkgrnd и биты cmdflag игнорируются — только простые команды.

## 3. Шпаргалка: управление процессами
• pid_t fork(void): 0 в дочернем процессе, PID ребёнка в родителе, -1 при ошибке.
• int execvp(const char *file, char *const argv[]): массив argv обязан заканчиваться NULL; при ошибке возвращает -1 и устанавливает errno.
• pid_t waitpid(pid_t pid, int *status, int options): pid > 0 — ждать конкретный процесс, options = 0 — блокирующее ожидание.
• WIFEXITED(status): истина, если процесс завершился сам (exit/return).
• WEXITSTATUS(status): код завершения 0–255 (применим только при WIFEXITED).
• WIFSIGNALED(status), WTERMSIG(status): завершение по сигналу и его номер.
• void perror(const char *s): печатает вашу строку и текст ошибки по errno.
• void _exit(int status): немедленное завершение без очистки буферов stdio.
ВАЖНО
• После неудачного execvp обязателен _exit(127), а не exit(): в потомке после fork нельзя выполнять очистку stdio родителя. 127 — стандартный код shell для «command not found».
• Ждать нужно именно своего потомка: waitpid(pid, &status, 0).
• Перенаправления, '&' и '|' в этой задаче не реализованы: не вводите их. Например, cat < file заставит cat читать терминал и «съест» следующие введённые команды.
• Ctrl+C пока завершает сам shell (обработка сигналов — отдельная задача). Для выхода используйте Ctrl+D.

## 5. Алгоритм решения
1. Сохраните каркас из задачи 12 (приглашение, promptline, parseline, отладочный блок).
2. На месте комментария /* FORK AND EXECUTE */ организуйте цикл for по i от 0 до ncmds-1: каждая команда выполняется отдельно и последовательно.
3. В теле цикла вызовите pid = fork() и разберите три случая: pid < 0, pid == 0, pid > 0.
4. Дочерний процесс (pid == 0):
- Вызовите execvp(cmds[i].cmdargs[0], cmds[i].cmdargs).
- Сразу после вызова (выполнится только при неудаче): perror(cmds[i].cmdargs[0]) и _exit(127).
5. Родительский процесс (pid > 0):
- Вызовите waitpid(pid, &status, 0); при возврате -1 — perror("waitpid").
- Если WIFEXITED(status) и код завершения не равен 0 — выведите в stderr сообщение вида: Command exited with status N.
- Если WIFSIGNALED(status) — выведите в stderr сообщение вида: Command terminated by signal.
6. Ошибка fork (pid < 0): perror("fork"), продолжайте цикл чтения команд.
7. Перенаправления и фоновый режим не добавляйте — это задачи 14 и 15.

## 2. Ключевые концепции для понимания задачи
• Фоновый режим: символ '&' в конце строки уже распознан parseline(), он изъят из аргументов и поднял глобальный флаг bkgrnd. Вручную искать '&' в массиве аргументов не нужно.
• Изменение касается только родительской ветки после fork(): при bkgrnd != 0 родитель НЕ вызывает блокирующий waitpid и сразу печатает PID потомка.
• Формат вывода: "[PID]" на стандартный вывод, как в bash. Приглашение появляется немедленно, потомок работает параллельно.
• Foreground не меняется: при bkgrnd == 0 родитель по-прежнему ждёт завершения через waitpid(pid, &status, 0).
• Жизненный цикл потомков: после завершения shell фоновые процессы продолжают работать, их «усыновляет» init (PID 1).
• Зомби: завершившийся потомок, статус которого родитель не забрал, остаётся записью в таблице процессов. В базовой версии это допустимо; сбор статусов — необязательное расширение.

## 3. Шпаргалка: фоновые процессы
• char bkgrnd: глобальный флаг из parseline(); ненулевой, если в строке был '&'.
• printf("[%d]\n", pid): вывод идентификатора фонового процесса (pid — значение, вернувшееся fork() в родителе).
• pid_t waitpid(pid_t pid, int *status, int options):
- pid > 0 — ждать конкретный процесс; pid = -1 — любой дочерний;
- options = 0 — блокирующее ожидание; WNOHANG — не блокировать, вернуть 0, если никто не завершился.
• ps -ef | grep sleep (в другом терминале): просмотр запущенных фоновых процессов.

• В фоновом режиме блокирующий waitpid вызывать нельзя — иначе смысл '&' теряется.

15. Перенаправление ввода/вывода (задание №4 по shell)
Измените вашу программу так, чтобы позволить перенаправление ввода/вывода. Заметьте, что перенаправление ввода ("< filename") используется только с первой командой в строке, а вывода ("> filename" или ">> filename") - только с последней.
Совет: используйте dup(2).

## 1. Подготовка рабочего места
Создаём отдельную папку и переносим файлы предыдущей задачи:

## 2. Ключевые концепции для понимания задачи
• Три стандартных дескриптора: stdin = 0 (STDIN_FILENO), stdout = 1 (STDOUT_FILENO), stderr = 2 (STDERR_FILENO). Перенаправление — это подмена этих дескрипторов на файловый.
• dup2(oldfd, newfd): закрывает newfd и делает его копией oldfd. После dup2(fd, 0) программа читает из файла, «думая», что читает терминал.
• Порядок действий в потомке: fork() → open() → dup2() → close(fd) → execvp(). Вызов exec заменяет образ процесса, но сохраняет открытые дескрипторы — поэтому подмена делается ДО exec.
• Правило первой/последней команды: '<' применяется только к команде с i == 0, '>' и '>>' — только к команде с i == ncmds - 1. Одиночная команда является и первой, и последней, поэтому работают оба перенаправления.
• Имена файлов уже разобраны: parseline() заполняет глобальные infile, outfile, appfile — разбирать строку заново не нужно.
• Режимы открытия: O_RDONLY для '<'; O_WRONLY|O_CREAT|O_TRUNC для '>' (перезапись); O_WRONLY|O_CREAT|O_APPEND для '>>' (дописывание). Права создаваемого файла — 0644.

## 3. Шпаргалка: перенаправление ввода/вывода
• int open(const char *path, int flags, mode_t mode): возвращает наименьший свободный дескриптор или -1 при ошибке.
• Флаги: O_RDONLY, O_WRONLY, O_CREAT (создать, если нет), O_TRUNC (обнулить при открытии), O_APPEND (запись всегда в конец).
• int dup2(int oldfd, int newfd): подменяет newfd копией oldfd; при ошибке возвращает -1.
• int close(int fd): закрывает дескриптор. После dup2 исходный fd закрывают — стандартный поток продолжает работать.
• STDIN_FILENO, STDOUT_FILENO, STDERR_FILENO: константы 0, 1, 2 из unistd.h.
• void perror(const char *s): сообщение об ошибке; при неудачном open передавайте имя файла.
ВАЖНО
• Перенаправление выполняется В ДОЧЕРНЕМ процессе до execvp, иначе shell испортит собственные потоки.
• В условии упомянут dup(2); на практике удобнее dup2(2) — он сам закрывает целевой дескриптор.
• При ошибке open: perror(имя файла) и _exit(1) в потомке; сам shell должен продолжить работу.
• Кавычки парсер не обрабатывает: пишите echo hello world, а не echo "hello world". Тестовые файлы создавайте в обычном терминале до запуска myshell.
• Конвейеры '|' по-прежнему не реализованы — в тестах не используются.

## 5. Алгоритм решения

2. В дочерней ветке (pid == 0) ПЕРЕД execvp добавьте три независимых блока перенаправления:
